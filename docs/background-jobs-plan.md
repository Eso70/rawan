# Part 11 implementation plan

Inspection: the existing worker is a single startup log; Redis/BullMQ are absent. API liveness is independent of dependencies. MediaCleanup already survives database cascades and upload rollback. Deletion remains synchronous and retryable. No public product operation currently needs asynchronous job status.

1. Infrastructure: add a small shared backend package for BullMQ connection/policy and reusable storage. Use stable BullMQ with one compatible Redis client, no Nest wrapper dependency. Redis URL is required by worker; API queues are disabled until explicitly configured outside production. Production requires Redis URL. Local Compose runs only Redis with AOF and noeviction.
2. Contracts: use a separate internal `@rawan/types/jobs` entry point. Centralize maintenance queue, media reconciliation job, versioned minimal payload, result, and runtime validation. Payloads contain no filenames, keys, or user-supplied resource IDs.
3. Producer: a managed API JobsModule owns one long-lived producer. A BullMQ scheduler periodically publishes reconciliation. Registration retries safely after Redis outages; ordinary CRUD stays available. An explicit operator CLI can enqueue one reconciliation run and inspect a safe internal status. No arbitrary public enqueue/status route.
4. Worker: evolve apps/worker into a lightweight TypeScript consumer with validated configuration, structured safe logs, Prisma 7 PostgreSQL adapter, shared local storage, modest concurrency, and bounded startup/shutdown behavior.
5. Lifecycle: BullMQ is authoritative for internal job status; completed/failed jobs have bounded count/age retention. No speculative BackgroundJob model or public job API now. Part 12 can add domain-owned durable user-facing jobs.
6. First job: reconcile at most 100 MediaCleanup records older than one hour. Keep Part 10 deletion semantics and operator fallback. Load immutable keys from PostgreSQL rather than queue payloads. Successful object deletion precedes removal of the cleanup record. Repeat execution and missing objects are safe.
7. Reliability: three attempts with exponential backoff, permanent invalid payload/provider/key errors fail immediately, transient DB/storage failures retry. Existing durable cleanup records provide recoverable delivery across PostgreSQL/Redis failure windows; no new full transactional outbox. Periodic reconciliation rediscovers pending records after outages.
8. Readiness: keep liveness unchanged. A separate queue readiness check returns a safe enabled/ready state and 503 on queue outage, with a strict timeout. No credential/stack/path disclosure.
9. Configuration: REDIS_URL, QUEUE_PREFIX, MEDIA_CLEANUP_INTERVAL_MS, WORKER_CONCURRENCY, and existing DATABASE_URL/MEDIA_LOCAL_PATH. Shared validation and paths must resolve to the same storage root for both applications. Worker environment loads API settings as development fallback, then its own override; production uses explicit environment.
10. Tests: pure contracts/config/processor unit tests, existing API HTTP regressions, real Redis producer/worker tests with explicit TEST_REDIS_URL and random checked namespaces, real PostgreSQL plus temporary storage, retry/permanent failure/idempotency/offline-worker/restart/outage/shutdown cases. No FLUSHALL/FLUSHDB. Bounded waits and complete teardown.
11. Verification: focused builds/checks at each phase, then Prisma, complete root/worker/API checks, safe integration tests, CI Redis service, frozen installation, formatting, and the twenty-question security review. Document actual results and any limitations before stopping.

Queue identities and retention are centralized. Redis credentials never enter job payloads/logs/status. New processors can use this infrastructure later without adding AI, frontend, normal CRUD queues, WebSockets, or notifications here.
