# Rawan design implementation roadmap

19 October 2026 · research only. This roadmap does not authorize implementation. It interprets the mandatory [product horizons](../../product-horizons.md) using [current backend coverage](../../backend-horizon-2.md) and accepted ADRs, rather than treating historical research gaps as current facts.

## Repository evidence and precedence

Inspected current root structure and manifests: pnpm/Turbo monorepo, TypeScript ESM, Next 16.3.8/React 19.3 website, Nest API, PostgreSQL/Prisma, Redis/BullMQ worker. Website dependencies include Tabler, Motion, Three and Lenis; there is no shared UI package, graph engine, canvas editor package, rich-text editor or window-manager library established by its manifest. Dependency availability is not a design requirement or evidence a feature exists.

Current implementation references: [design system](../README.md), [principles](../design-principles.md), [typography](../typography.md), [components](../components.md), [onboarding guide](../../onboarding-guide.md). Product architecture research is useful for intent, but older statements that releases/readers/maps are absent are superseded by backend coverage, actual controllers/DTOs/schema and accepted ADRs 0001–0006. The existing site sample library and marketing demonstrations do not establish real reader or editor UI.

H2 means additional near-term contract/infrastructure work. H3 remains deferred platform exploration. ## Contract and security constraints for future agents

- Treat account preferences as presentation only. Continue JWT identity, project ownership and scoped not-found behavior; enforce setup at the server, not just through a redirect.
- Private project search, manuscript data and media must not be used as public reader content. Release snapshots explicitly approve copied content and assets. Deleted/unselected source IDs do not become public links.
- Respect actual bounded lists and request budgets. Current map detail reads are capped (1000 pins/100 regions); canvas detail reads cap nodes (1000) and outgoing edges per node (100). UI must not claim unbounded retrieval. Consult actual create limits and pagination behavior before promising scale.
- Scene content and semantic block updates have different contracts. WorkDocument updates use expectedRevision; do not assume all endpoints provide the same concurrency control. H2 rich content requires a content-format decision and relevant ADR, not arbitrary HTML in a string field.
- Preference DTO allows named values only. Reader font size 12–40, line height 1.2–2.5, width 320–1200 and supported comic modes constrain controls. No invented tutorial/graph/layout preference fields.
- Maps/pins/canvas references are owned project resources; deletion can leave unavailable visual references. Render that safely. Scene/entity mentions require an explicit persistence design if introduced.
- Current API/worker share storage/database responsibilities; imports/artwork/exports are asynchronous jobs. Reflect processing/failure rather than showing successful media immediately. AI stays disabled until explicitly configured.

## Approval questions for a later implementation phase

1. **Studio default:** retain existing navy as the first productive surface, or approve a neutral charcoal studio with sparse warm accent? Recommendation: review both on the same document before a global decision; preserve existing pages in either case.
2. **First useful workflow:** build project → manuscript first, or start with a specific worldbuilding workflow? Recommendation: project → manuscript, optional reference panel later.
3. **Initial manuscript target:** existing chapter/scene text or simpler WorkDocument sections/blocks? Recommendation: chapter/scene for a conventional novel workflow; choose WorkDocument explicitly for essays/structured prose rather than blending formats.
4. **Atmosphere default:** opt-in world/project background or enabled with an easy plain mode? Recommendation: opt-in outside existing onboarding, solid writing/reading by default.
5. **Tutorial persistence:** per-device voluntary dismissal first or new account-synchronized progress? Recommendation: per-device first, H2 only when cross-device value is demonstrated.
6. **Support destination:** existing approved contact/help links or a new feedback workflow? Recommendation: real content/links first; no simulated Send action.

These are review decisions for future work, not permission requests to complete the current documentation. New persistence/content/identity changes need an appropriate proposal and relevant ADR before implementation. The repository currently contains no installed Quiet Literary Studio skill; source docs and this user brief supply the design context.

## Risks and verification plan

Main risks: treating older research as current support status, overbuilding window management, using art as a contrast dependency, persisting unsupported schemas, losing draft edits, publishing private references, confusing tour completion with account access, and copying dense/low-contrast reference details.

Future verification must cover actual DTO limits, empty/loading/error/conflict/unavailable states, stale revisions, deleted references, reader withdrawal/resume fallback, keyboard-only completion, screen-reader structure, responsive/text zoom, reduced motion and plain backdrop. Test spatial tools with realistic dense data and a list/form alternative. Test important save/authorization behavior, not just screenshot resemblance. No application tests or live external provider calls are needed to certify this documentation-only change; links, inventories and consistency require review instead.
