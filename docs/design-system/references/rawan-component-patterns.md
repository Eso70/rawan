# Rawan component patterns — proposed specification

19 October 2026 · cumulative batches 1–2. [Visual evidence](vvd-visual-reference-analysis.md), [tokens](rawan-design-tokens-proposal.md), [layouts](rawan-workspace-layouts.md). This inventory is a design specification, not a mandate to build a component library in advance.

## Existing ownership and shared rules

The website has seven native primitives in `apps/website/src/components/ui/controls.ts`: Button, IconButton, TextInput, Checkbox, Radio, Select and FieldError. It also has a feature-styled language disclosure and actual search dialog. There is no shared UI workspace package. Reuse those primitives when semantics match, retain CSS Module recipes and keep data/session logic in features. Installed Tabler icons are sufficient for ordinary controls. Motion, Three and Lenis dependencies do not justify animating productive interfaces or adopting a rendering engine without need.

Every pattern below inherits this state contract: default, hover where relevant, keyboard focus, pressed/selected/expanded where meaningful, disabled with reason, and busy/error when asynchronous. Busy actions block duplicate submission and expose a named status; failure retains input, offers retry and avoids false success. Selected state uses text/shape and programmatic state, not color alone. Tooltips supplement accessible names and never contain the only essential instruction. Destinations use links, operations buttons, choices native inputs, and disclosures native details/summary when practical. An “empty” state is not a loading or permissions failure.

Shared accessibility requirements: visible labels, logical reading order, meaningful headings, focus never behind a dimmer, named icon actions, Escape where dismissible, and target areas preferably 44px. Respect text scaling and reduced motion. Do not announce every pointer movement or keystroke as a live region. Validation errors connect to their input and are focused or summarized when submission fails. The component does not derive authorization from preference values.

The tables specify purpose/anatomy/variants/states in the first column; behavior, accessibility, responsive treatment and intended consumers follow. All variants are proposals unless explicitly identified as existing.

## Implementation acceptance per real consumer

Before extracting a new pattern, identify its owning feature, data contract, failure states and actual second consumer. Verify tab order and keyboard operation, plain/reduced-motion modes, 320px width, text zoom and long localized-looking strings even while UI remains English. Check unavailable/deleted references and stale revisions without losing unsaved text. A prototype cannot mark synchronization or backend workflows delivered. Keep tutorial state, auth state, document data and decorative media readiness separate.
