# Mandatory product horizons and feature register

Classification date: 12 October 2026. This register applies to all expanded-product research in this repository. It classifies recommendations, not delivered screens or an approved roadmap. Classification itself does not implement features; the authorized backend implementation is recorded separately.

Implementation update: C13 and originally Horizon 2 N01–N26 are implemented as bounded backend capabilities, now H1 for future frontend consumption. See [current coverage and limits](backend-horizon-2.md), [validation ledger](backend-horizon-2-implementation.md) and accepted ADRs 0001–0006. H3 remains deferred. N IDs remain stable for traceability.

## Rules

- **HORIZON 1 — CURRENT RAWAN:** supported by the current backend and appropriate for the next frontend implementation. Client-only presentation is included only when it uses existing authorized resources and needs no new persistence/API. A backend capability does not mean its frontend already exists.
- **HORIZON 2 — NEAR FUTURE:** a logical extension requiring additional backend/product work. A suggested first milestone is still future work; it cannot be simulated with private owner endpoints, fabricated catalogue records or unsupported request fields.
- **HORIZON 3 — LONG-TERM PLATFORM:** strategic direction that informs naming, boundaries and branding today, but must not be implemented yet. Conceptual preparation is not permission to create speculative data models.

Each feature has one horizon for the scope stated in its row. Broader variants are separately classified; for example private draft preview and bounded released-work reading are now H1, while advanced offline distribution is H3. “Future” in earlier studies must be interpreted through this register rather than as an unspecified launch requirement.

Current backend support is established from the [schema](../packages/database/prisma/schema.prisma), [reviewed OpenAPI contract](contracts/backend-v1.openapi.json) and implemented services/DTOs. UI labels, marketing demonstrations, database fields without appropriate public endpoints, onboarding interests and queue infrastructure do not establish missing features.

The tables answer the six required questions for each major feature. Feature IDs let each study link its recommendations to the same classification instead of maintaining inconsistent duplicate gap tables.

## ADR policy

An ADR records an agreed architectural decision, alternatives and consequences; it is not a feature proposal marked complete. **Yes — Axx** means an ADR is needed before that feature's architecture/schema/API is implemented, or the feature must be explicitly covered by that topic's decision. Related features can share one ADR. **No** means routine frontend composition or an existing contract needs no new architectural decision for the bounded scope listed.

Long-term concepts can be explored now without recording speculative decisions as accepted ADRs. Accepted implementation decisions are recorded separately in ADRs 0001–0006. UI research and experiments can precede an ADR; decisions changing identity, permissions, persistence, content format or lifecycle require the relevant decision before implementation.

## Reading the register alongside research

Every expanded-product study includes a Mandatory product horizons section mapping its major recommendations to these IDs. Detailed controls, metadata fields and responsive requirements inherit the classification of their feature scope. An unregistered recommendation must be classified before it is treated as an implementation candidate.

Examples: local creator typography is C10/H1; a released reader backend is implemented N03/H1 and synchronized reader preference persistence is implemented N16/H1; their UI remains unimplemented by this task. Private project characters are C04/H1; selected released characters are implemented N15/H1; an independent shared-universe catalogue is L02/H3.

Research prose, diagrams and rollout examples do not override this classification. Some diagrams mix existing and proposed entities; their future portions must remain future. Horizon membership is not a promise, deadline, order of approval or accessibility/production-readiness certification.

## Maintenance and scope gates

Before moving a feature between horizons, verify implemented schema, routes, request/response types, access checks and appropriate validation; update this register and affected studies deliberately. Do not promote N04 to H1 because an empty reader dashboard or a hardcoded book grid exists.

Before a future feature is implemented, its proposal must identify feature scope/ID, current support, backend gap, frontend/data implications, required ADR decision and dependencies. H3 remains research only. The current authorized task implements N01–N26 backend scopes only; the original studies and deferred H3 possibilities remain distinct.
